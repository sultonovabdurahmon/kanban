# Анализ предметной области: Kanban — система управления командными задачами

## 1. Организация

В качестве предметной области рассматривается работа небольшой проектной команды, которая совместно выполняет задачи в рамках одного или нескольких проектов. В команде есть руководитель проекта и участники, отвечающие за выполнение назначенных им задач. Руководитель формирует проекты, добавляет участников, распределяет работу, устанавливает сроки и контролирует ход выполнения. Участники получают назначенные задачи, уточняют требования, выполняют работу и сообщают о результатах. Для контроля используется Kanban-доска, на которой задачи перемещаются между колонками в соответствии с их текущим состоянием. Разрабатываемое веб-приложение должно объединить сведения о проектах, участниках, задачах, комментариях, вложениях и истории изменений в одном месте.

### Проблемы текущего процесса

1. Информация о задачах может храниться в разных местах — сообщениях, таблицах и отдельных заметках, поэтому команде сложно поддерживать единый актуальный список работ.
2. Руководителю трудно быстро определить ответственного за задачу, её текущий статус и наличие просрочки без ручного уточнения у участников.
3. Изменения сроков, исполнителей и статусов не всегда фиксируются в единой истории, из-за чего сложно установить, кто и когда изменил задачу.

*Примечание: описание организации является моделью предметной области учебного проекта. Конкретная компания-заказчик и количественные показатели её работы не предоставлены.*

## 2. Акторы

| Роль в системе | Кто это | Что делает в системе |
|---|---|---|
| `admin` | Администратор системы | Управляет учётными записями и основными настройками системы, контролирует доступ пользователей |
| `manager` | Руководитель проекта | Создаёт проекты, добавляет участников, формирует колонки Kanban-доски, создаёт и распределяет задачи, контролирует сроки и ход выполнения |
| `member` | Участник проекта | Просматривает доступные ему проекты и назначенные задачи, меняет статус задачи в пределах разрешений, добавляет комментарии и вложения |

Один человек может иметь разные роли в разных проектах, если это предусмотрено настройками доступа. Актор обозначает роль в системе, а не конкретного человека.

## 3. Бизнес-процессы

| Процесс | Участники | Начало процесса | Результат |
|---|---|---|---|
| Создание проекта и добавление команды | `manager` | Возникает необходимость организовать работу над новым проектом | Создан проект, определены участники и доступ к проекту |
| Создание и назначение задачи | `manager` | Нужно поручить участнику конкретную работу | Создана задача с описанием, приоритетом, исполнителем и сроком |
| Выполнение и изменение статуса задачи | `member`, `manager` | Участник приступает к назначенной задаче или завершает этап работы | Статус задачи обновлён на Kanban-доске |
| Обсуждение задачи и добавление материалов | `member`, `manager` | Возникает необходимость уточнить задачу или приложить рабочие материалы | В задаче сохранены комментарии и вложения |
| Контроль сроков и просмотр истории | `manager`, `member` | Требуется проверить ход проекта или выяснить причину изменения | Получен список задач с фильтрами, выявлены просроченные задачи, просмотрена история изменений |

### 3.1. Выполнение задачи на Kanban-доске (подробно)

**Участники:** `manager`, `member`.

**Начало:** руководитель проекта создаёт задачу и назначает её участнику.

1. Руководитель открывает нужный проект и создаёт новую задачу.
2. В задаче указываются название, описание, приоритет и срок выполнения.
3. Руководитель назначает ответственного участника и сохраняет задачу.
4. Новая задача появляется в начальной колонке Kanban-доски, например «К выполнению».
5. Участник открывает задачу, изучает описание и при необходимости задаёт уточняющий вопрос в комментариях.
6. После начала работы участник перемещает карточку в колонку «В работе». Система сохраняет новое состояние задачи и запись об изменении в истории.
7. По мере выполнения участник добавляет комментарии и необходимые вложения.
8. После завершения работы участник перемещает карточку в колонку «Готово».
9. Руководитель проверяет результат и при необходимости оставляет комментарий или возвращает задачу на доработку.

**Результат:** задача имеет актуальный статус, назначенного исполнителя, срок и историю изменений; команда может определить состояние работы на Kanban-доске.

## 4. Объекты данных

| Объект | Основные сведения |
|---|---|
| Пользователь (`users`) | имя, адрес электронной почты, хеш пароля, роль, дата регистрации |
| Проект (`projects`) | название, описание, дата создания, создатель, статус проекта |
| Участник проекта (`project_members`) | идентификатор проекта, идентификатор пользователя, роль в проекте, дата добавления |
| Колонка Kanban (`columns`) | название, позиция на доске, идентификатор проекта |
| Задача (`tasks`) | название, описание, исполнитель, срок выполнения, приоритет, статус/колонка, дата создания |
| Комментарий (`task_comments`) | текст комментария, автор, задача, дата публикации |
| История задачи (`task_history`) | задача, пользователь, тип изменения, старое значение, новое значение, дата изменения |
| Вложение (`task_attachments`) | задача, имя файла, путь к файлу, тип файла, автор загрузки, дата загрузки |

Объекты соответствуют процессам создания проектов, распределения задач, совместной работы и контроля изменений. Связь участника с проектом хранится отдельно, поскольку один пользователь может участвовать в нескольких проектах.

## 5. Глоссарий

| Термин | Определение |
|---|---|
| Kanban-доска | Рабочая доска проекта, на которой задачи отображаются карточками и распределяются по колонкам |
| Карточка задачи | Представление отдельной задачи с названием, описанием, исполнителем, сроком и приоритетом |
| Колонка | Этап рабочего процесса, например «К выполнению», «В работе» или «Готово» |
| Исполнитель | Участник проекта, которому назначено выполнение задачи |
| Комментарий | Текстовое сообщение участника или руководителя, связанное с конкретной задачей |
| Приоритет | Уровень важности задачи, определяющий очерёдность её выполнения |
| Просроченная задача | Задача, срок выполнения которой наступил или прошёл, а задача ещё не завершена |
| История изменений | Последовательность записей о том, кто, когда и какие данные задачи изменил |
| Вложение | Файл, прикреплённый к задаче для передачи материалов или подтверждающих документов |

## 6. Источники требований

Для учебного анализа использованы и предусмотрены следующие методы сбора требований:

1. **Анализ задания и описания проектной темы.** Из требований к Kanban-приложению выделены роли пользователей, основные процессы, поля задач, комментарии, вложения, фильтрация, перетаскивание карточек и журнал изменений. Этот источник отражает требования, заданные для учебного проекта.
2. **Структурированное интервью с потенциальным руководителем проекта или участником команды.** Интервью предлагается провести для проверки модельных предположений о реальном порядке работы. Ниже приведён список вопросов для такого интервью; ответы пока не получены.

### Вопросы для интервью

1. Как сейчас создаются проекты и кто отвечает за их организацию?
2. Каким способом участники получают новые задачи?
3. Какие сведения обязательно должны быть указаны в задаче?
4. Кто назначает исполнителя и может ли задача иметь нескольких исполнителей?
5. Какие этапы работы должны отображаться на Kanban-доске?
6. Кто имеет право менять статус задачи?
7. Как команда сообщает об изменении срока или возникшей проблеме?
8. Нужно ли прикреплять к задачам файлы и какие типы файлов используются?
9. Какие фильтры нужны руководителю для контроля задач?
10. Какие изменения необходимо сохранять в истории задачи?

*Примечание: интервью является планом сбора требований, а не утверждением о проведённом опросе. После интервью ответы следует добавить в документ и уточнить процессы и состав данных.*
